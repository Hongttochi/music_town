# MUSIC TOWN 멀티플레이 설정

## Supabase에서 직접 할 작업

SQL Editor에서 아래 파일을 순서대로 실행합니다. 첫 파일을 이미 실행했다면 두 번째부터 실행하면 됩니다.

1. `supabase/migrations/202611050001_member_profiles.sql`
2. `supabase/migrations/202611050002_multiplayer.sql`

두 번째 SQL은 채널 5개(각 30명), 무대 위치 6개, 접속 세션, 현재 공연, FIFO 대기열을 생성합니다. Realtime의 `supabase_realtime` publication에 `town_channels`를 추가하는 설정도 포함합니다. 이미 존재하는 채널·무대 데이터는 초기화하지 않습니다.

실행 후 앱을 새로고침하세요. 브라우저에는 기존 URL과 Publishable key만 사용합니다. 새 Secret key나 service_role 키는 필요하지 않습니다.

## 동작

- 로그인 시 프로필·캐릭터를 DB에서 불러옵니다. 등록/수정 완료 시 DB에 저장합니다.
- 접속 채널과 사용자 위치는 서버 세션에 저장합니다. 1.5초마다 위치와 생존 신호를 보내고 상대 캐릭터는 보간해서 움직입니다.
- 채널 revision을 Realtime으로 구독하며, 주기적인 동기화가 끊긴 이벤트를 보완합니다.
- 한 계정은 하나의 공원 세션만 유지합니다. 다른 탭에서 새로 입장하면 이전 탭의 조작 권한은 만료됩니다.
- 관람객은 무대 신청을 할 수 없습니다. 이 제한은 UI뿐 아니라 DB에서도 검사합니다.
- 각 채널의 각 무대에는 한 명만 공연할 수 있습니다. 한 사람은 공연 또는 대기 한 곳에만 참여합니다.
- 공연은 최대 5분이며 조기 종료할 수 있습니다. 서버 순서에 따라 다음 대기자가 승계합니다.
- 채널 이동 및 정상 로그아웃 시 공연·대기를 정리합니다. 브라우저 종료, 네트워크 단절은 마지막 신호로부터 45초 후 정리합니다.
- 만료 정리는 다음 서버 요청에서 수행됩니다. 이용자가 전혀 없을 때는 물리적인 행 삭제가 지연되지만, 다음 접속 전에 정리하므로 정원이나 대기 순서에 오래된 세션이 남지 않습니다.
- 모든 정원 검사와 공연·대기 변경을 DB 트랜잭션에서 직렬화하여 중복 점유를 방지합니다.

## 데이터 공개 범위

개인 프로필 테이블은 본인만 직접 읽고 수정합니다. 같은 채널에 입장한 사용자에게는 RPC가 캐릭터·닉네임·소개·SNS 링크·위치·역할을 전달합니다. 이메일, 인증 정보와 내부 클라이언트 식별자는 전달하지 않습니다. 다른 채널에서는 인원수만 보입니다. 세션·공연·대기열 테이블은 클라이언트 직접 쓰기를 허용하지 않습니다.

## 확인 방법

1. 서로 다른 두 계정으로 두 브라우저에서 로그인합니다.
2. 같은 채널 입장 후 인원과 캐릭터가 서로 보이고 이동이 반영되는지 확인합니다.
3. 두 뮤지션이 같은 무대에 신청합니다. 한 명은 공연, 다른 한 명은 대기 상태여야 합니다.
4. 첫 뮤지션이 종료하면 대기자가 무대로 이동해야 합니다.
5. 관람객 계정은 공연 신청이 차단되어야 합니다.
6. 채널을 바꾸면 이전 채널에서 캐릭터가 사라지고 대기가 취소되어야 합니다.
7. 탭 종료 후 약 45초 뒤 다른 브라우저에서 인원이 줄어드는지 확인합니다.

## 검증 범위와 남은 기능

`node --test tests/multiplayer.test.mjs`는 PGlite의 실제 PostgreSQL 엔진에서 마이그레이션, RLS, 권한 거부, 정원, 무대 중복 방지, FIFO 승계, 만료, 채널 분리, 재실행을 검사합니다. 호스팅된 Supabase의 Realtime 연결과 여러 실제 브라우저의 동시 동작은 SQL 적용 후 위 단계로 확인해야 합니다.

실시간 음성 송출은 LiveKit 연결 설정 후 사용할 수 있습니다. 설정 방법과 검증 범위는 [실시간 음성 설정](live-audio-setup.md)을 참고하세요. 공유 응원 반응 및 실제 팔로우 서버 처리는 별도 기능입니다. 이동은 1.5초 단위이므로 빠른 게임 수준의 이동 동기화는 아니며, 최대 인원 부하 시험도 별도로 필요합니다.

참고: https://supabase.com/docs/guides/realtime/postgres-changes

## 설정에서 계정 탈퇴

설정의 ‘탈퇴하기’에서 삭제 확인 후 `/api/delete-account`를 호출합니다. 서버가 Supabase Auth로 로그인 토큰을 검증한 뒤, 확인된 본인 ID만 Admin API로 삭제합니다. 브라우저가 전달한 다른 사용자 ID는 사용하지 않습니다. 실제 계정 삭제 성공 후 이 기기의 로그인 세션과 해당 계정의 로컬 프로필·캐릭터·팔로우 캐시를 정리합니다. Google·Kakao 계정 자체를 삭제하는 기능은 아닙니다.

Vercel 서버 환경에 `SUPABASE_SECRET_KEY`를 설정하고 재배포해야 합니다. 기존 `SUPABASE_SERVICE_ROLE_KEY`도 지원합니다. 이 값에 `VITE_` 접두사를 붙이면 안 됩니다. URL과 공개 키는 기존 `VITE_SUPABASE_URL`, `VITE_SUPABASE_PUBLISHABLE_KEY`를 사용합니다. 서버 키가 없으면 API는 503으로 실패하며 계정을 삭제하지 않습니다.

운영 적용 전 테스트 계정으로 `auth.users` 삭제가 프로필·공원 세션·공연·대기열의 외래키 정리와 연결되는지 확인하세요. 이 체크아웃에는 기존 문서가 참조하는 DB 마이그레이션이 없어 원격 삭제 연쇄를 검증하지 못했습니다. Storage 소유 객체나 삭제 제한 외래키가 있으면 Admin API 삭제가 실패할 수 있습니다. 실패 시 앱은 탈퇴 완료로 표시하지 않습니다. 삭제된 사용자의 기존 JWT는 만료 전까지 일부 API에서 허용될 수 있으므로 민감한 서버 작업은 Auth 사용자 존재 여부도 확인해야 합니다.

검증: `node --test tests/delete-account.test.mjs`는 본인 인증, 위조 대상 ID 무시, 확인 누락, 만료 세션, 서버 설정 누락, 서버 오류를 검사합니다. 실제 운영 계정 삭제는 실행하지 않습니다.

참고: https://supabase.com/docs/reference/javascript/auth-admin-deleteuser · https://supabase.com/docs/guides/auth/managing-user-data
